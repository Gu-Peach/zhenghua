# 单页初扫失败继续后续页

后续用户要求遍历结束即处理完成，本文中“遍历后失败汇总”的早期约定已由[完成状态调整](./2026-10-18-extraction-finished-status.md)替代。单页失败隔离、历史诊断及成功缓存规则保持。

## 问题与行为

run `553553fa-4355-52e0-98b2-e6c13e871700` 的 PDF 第175页（010R22）在初扫输出32768 tokens后被截断。初扫层已经记录错误，但保存页节点将 `scan_failed` 升级为文档异常，后续页未执行。

页面子图现按初扫结果分流：成功页继续规划/补全/校验/保存；失败页保存失败尝试后结束本页，文档循环继续下一页。失败页不进入 `processed_pages` 或已完成页缓存，也不生成空白成功记录。其他页仍可使用其已渲染图像作为目标证据。

- 平台通过既有 `scan` 事件发布 `scan_failed` 阶段、页面 `failed` 状态和独立尝试快照。该事件不会将整个任务终止。
- 本地将失败尝试保存为 `agent/failed-pages/<PDF物理页>/<UUID>.json`，汇总保留在 `errors.json` 和 `run-result.json`。
- 完整遍历结束仍有提取错误时，Worker使用既有 `failed` 终态，错误码为 `EXTRACTION_PARTIAL`，提示其他页已处理，并保留错误清单及重试入口。不新增“部分完成”数据库状态。
- 恢复时复用已有成功页，重新处理没有成功缓存的页；之前失败尝试不删除。
- 配置、权限、存储、租约和取消仍立即中止；没有扩大原有初扫异常捕获范围。跨页补全原有逐连接失败策略保持。

未改变模型请求、Prompt、业务字段或Profile版本；运行来源摘要同步。没有数据库迁移或API字段变更，现有前端已支持失败页状态及后台错误消息。

## 验证与启用

- 4个修改文件通过Ruff及AST解析；实际LangGraph构建确认两条条件边和独立失败结束边，未执行Graph或模型。
- 4个Profile绑定及98项运行来源摘要核对通过；`git diff --check`通过。
- 3个源码文件定向mypy仍有5条原有类型问题，与先前入口对齐记录中的问题对应；新增代码没有额外报告。
- 补充本地/增量平台两种失败后继续、恢复只重试失败页、失败历史保留及Worker遍历后汇总的回归代码，未运行pytest、Fake VLM或真实模型。
- 未重启服务、重跑现有任务、写业务数据库或Storage。现有失败任务仍保持原状。

由用户重启实际提取Worker后，在原项目点击“重试提取”；模型、Profile冻结包和配置保持原样时，已完成页会复用，第175页若再次失败会继续第176页。若运行时采用内嵌Worker，重启对应宿主。无需为此重新上传整份PDF。
