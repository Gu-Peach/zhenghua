# Explain流式失败排查与脱敏诊断

## 已取得证据

窗口关闭重开会卸载组件，新挂载生成conversation_id；同窗口追问复用conversation_id并生成新turn_id，重试才复用原turn_id。未发现关闭窗口后继续累积同一应用会话的行为。

旧错误只保存ModelGatewayError分类，Explain没有开启持久模型Trace，无法回溯旧失败的原始error帧。实际图纸对照探针被自动审批拒绝，未执行；随后用户明确批准最多3次无项目数据诊断，已全部使用，没有第四次调用。

对当前配置api.3stooges.chat / Qwen3.8 27B，使用虚构文字、diagnostic_noop定义和固定空白图进行3次受控SSE请求：纯文字18 tokens、文字+工具326 tokens、空白图+工具398 tokens，全部成功，耗时约0.500/0.485/0.516秒，总742 tokens；供应方均报告cached_tokens=0。没有执行模型返回工具，没有项目图纸/记录/历史外传。费用未计算；无缓存命中不能证明供应商全局未开启缓存。

本地只读Fake重建该页当前数据：9行、事实包50,403字符；初次模型请求文本54,560字符，工具定义6,924字符。模拟看2图后的下一工具轮次文本54,648字符，图像URL编码合计246,296字符；以虚构短历史模拟修改追问文本54,645字符，工具定义9,456字符。证据展示路径合计约2.6万字符，包含重复事实。此为当前数据重建，不是旧失败轮次原始payload；字符数和图片编码体积不是token数，不能据此判定已超限。

因此仅证明当前基础小请求/简单工具/小图片协议可用，未复现旧错误；大上下文/真实多图请求限制与服务间歇性错误仍有待现场诊断。没有自行更改模型、截断事实或调整规则来掩盖未知原因。

## 诊断实现

新增ExplainDiagnosticGateway，默认真实工厂接入。每次invoke/stream独立诊断UUID，记录文本/图片编码计数、工具Schema计数、历史消息量、工具轮次、已返回工具数量/名称、conversation_id、耗时、数字usage和finish_reason。仅聚合计数，不保存请求正文、工具参数、回答、图像、URL和凭据。

错误只保存稳定错误码、受限符号型provider_code/type及技术关键词分类：context_limit、memory_capacity、tool_compatibility、model_checkpoint、rate_limit或unknown。原始provider_message不落盘、不打印，未知不猜测OOM。错误界面在原有错误码下显示安全分类及诊断编号，终端可按编号查统计。日志位于忽略目录.runtime/explain-diagnostics，唯一文件原子写入；保存失败不改变原结果。不增加模型重试或模型调用。
