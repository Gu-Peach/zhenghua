# 主助手重扫执行回执校验

真实会话中，“GCR102图纸的线表重新扫面一遍”没有产生任何工具调用，模型却返回自造任务号和queued状态。旧逻辑在tool_calls为空时直接输出文本，只拦截少数发布/修改词，未覆盖重扫口述成功。

修复位于 `main_assistant/completion.py`、`service.py` 和 `prompt.md`：

- 无工具终答在发送前增加一次短结构化核验，判断用户所需业务工具及答复是否声称执行。按语义区分明确重扫（含“扫面”笔误）、仅解释机制、拒绝执行和普通问候，不靠“已创建”关键词判定任务启动。
- 用户要求执行但缺对应回执时丢弃原答复，最多发起一轮受控补调；补调可以先检索定位，但仅找到图纸不算重扫成功。仍缺执行回执则发error并结束为失败，不转发“好的我来处理”等承诺。
- 真实检索返回多个候选或没有目标时可以要求选择/补充；不猜一个项目启动重扫。权限/参数/工具失败不会变成成功任务卡。
- start_rescan回执需要有效action/run UUID及合法状态；启动确认由程序从回执构造，不再要求模型改写任务编号。业务提交仍需原候选确认。
- completed携带verification_version、required_tool、disposition及action/run引用，供Server核对。专业Agent直出答复也必须有真实action引用。

正常检索/普通聊天的最终答复会多一次短分类调用；直接取得重扫回执或专业Agent直出时不增加这次核验调用。未修改共享网关、提取算法、Prompt规则包或数据库Schema。

14项主助手离线测试通过，覆盖原始虚假编号、补调成功/仍不调用、只承诺/只检索、失败/无效回执、普通对话/机制解释、歧义选择和真实编号直出。另有一次实际Agent→Server业务Facade→模拟数据库→SSE回执贯通测试，验证重试只入队一次。全部Fake Gateway/MockTransport，无真实模型或重扫。

重载8100和8000后重新发送需求。历史错误答复保留为历史文本，不会自动补执行；重放旧版未核验的成功流会被Server拒绝并提示重新发送。
