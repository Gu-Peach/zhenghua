# Explain HTTP400：强制工具选择不兼容

## 现场证据

截图诊断编号`1ee75dfa-19fe-4f83-a733-2a9f29770339`对应北京时间12:28:51，供应方返回HTTP400、`provider_code=tool_choice_not_supported`。同轮12:28:39也有相同拒绝。首答正常stop但没有工具，随后补调携带`tool_choice=required`被拒绝；补调有1张实际图片、约20359文本字符，未执行重扫工具。

因此本次根因是上一轮加入的required参数与当前模型服务不兼容，不能解释成鉴权失败、图片未上传、Worker错误或仅因没重启8100。日志本身已证明该次请求执行了required与图片输入分支。

只读核对之前12:25:44创建的任务已于12:27:38取消；本次失败未新增任务。本轮未改任务状态。

## 修订

- 仅HTTP400且错误码精确为tool_choice_not_supported时启用兼容分支；其他400、401、模型故障保持原错误，不额外调用模型或静默换参数。
- 使用Pydantic判别联合生成JSON Schema，让模型返回重扫/精确查询/看图/追问决策；该请求不发送tools、tool_choice或response_format。普通自然语言不能成为任务，未知操作、范围缺失、身份覆盖、非法Schema均拒绝，result_mode仍由程序决定。
- 有效决策转换成原受控工具调用，复用原参数校验、权限、范围、幂等和回执检查；只有真实入队后才报告任务ID/状态。结构化模式仅保持本轮，检索后用更新事实继续，仍受8次工具预算限制；已有任务后直接展示回执。
- 精简事实和本轮原图/附件视觉输入继续传递，不把旧无回执答复或工具协议残片作为结构化输入。
- 诊断按provider_code识别“强制工具选择不兼容”，区别于全面不支持工具调用。返回工具数改存metadata，避免被TraceStore白名单丢弃；仍只保存安全计数/分类。

无HTTP DTO、OpenAPI、数据库、前端、Worker或Profile变化，无迁移。实现集中在`tool_compatibility.py`、Explain Graph与诊断/安全错误提示。
